# Semantic Layer Architecture

Updated: 2026-06-25

This document defines how Twin Base Studio should model the semantic layer of a city digital twin before adding more semantic packs or city-specific logic.

## Purpose

The semantic layer must not be treated as a visual decoration or as a loose set of map layers. It is the contract that lets the platform understand what a city object is, what role it plays, what evidence supports that meaning, and which operational modules can safely use it.

Operational city workflows have a separate standard in
`MUNICIPAL_OPERATIONAL_WORKFLOW_STANDARD.md`. That document defines the boundary
between the twin/evidence layer and the official municipal process where a city
reviews, approves, rejects, dispatches, or records decisions.

The platform keeps four concepts separate:

1. Physical entity: the thing that exists in the city.
2. Semantic class: the broad meaning used for query, rendering, and API contracts.
3. Semantic attributes or tags: the detailed meaning attached to an entity.
4. Semantic pack: an installable operational module that uses semantic entities to produce indicators, workflows, exports, and review decisions.

## Conceptual Model

### Physical Entity

A physical entity is the city object stored in the base twin. Examples include buildings, roads, parcels, parks, water bodies, transit stops, street lights, electric poles, water pipes, sewer pipes, stormwater inlets, pump stations, sensors, and BIM or asset-management objects.

Physical entities live primarily in PostGIS. They need stable identifiers, geometry, provenance, authority status, confidence, lifecycle status, and specialized attributes.

### Semantic Class

A semantic class is the broad meaning used by the query engine, viewers, APIs, and exports. It groups physical entity types into stable product-facing families.

Initial target semantic classes:

- `builtFabric`: buildings, structures, BIM assets, and construction-related objects.
- `mobilityNetwork`: roads, paths, transit corridors, stations, mobility assets, and access routes.
- `greenBlue`: parks, water, forest, wetlands, protected/ecological areas, and open environmental systems.
- `landUse`: residential, industrial, commercial, vacant, mixed-use, zoning, and coverage-gap areas.
- `utilityNetwork`: water, sewer, stormwater, power, lighting, telecom, and other infrastructure networks.
- `civicServices`: public facilities, civic points, schools, health, emergency, waste, and service anchors.
- `places`: settlements, neighborhoods, landmarks, named public places, and orientation anchors.
- `liveContext`: sensors, devices, feeds, observations, and broker-projected live entities.
- `providerEvidence`: source/provider overlays used for review and provenance.
- `semanticPackOutputs`: derived operational features generated by semantic packs.

The current code exposes a first-generation vocabulary under names such as `buildings`, `roads`, `greenBlue`, `places`, `accessSeeds`, `providerOverlays`, and `semanticPacks`. Those names are implementation generation one, not the complete long-term vocabulary.

### Semantic Attributes

Semantic attributes are object-level meanings. One entity may have many semantic attributes, and each attribute should carry provenance, confidence, method, source, and authority state.

Examples:

- a road can be `primary`, `secondary`, `residential`, `pedestrian`, `emergency_access_candidate`, or `high_traffic`;
- an area can be `green`, `water`, `industrial`, `residential`, `vacant`, `protected`, or `informal`;
- a pipe can be `potable_water`, `sewer`, `stormwater`, `main_pipe`, `distribution_pipe`, `high_pressure`, `critical_segment`, or `old_asset`;
- a building can be `residential`, `commercial`, `public_service`, `heritage`, `damaged`, `vacant`, or `authority_validated`.

### Semantic Pack

A semantic pack is not a base object class. It is an installable module that uses physical entities and semantic attributes to produce operational outputs.

Examples: Mobility Pack, Water Infrastructure Pack, Flood / Drainage Pack, Waste Pack, Heat / Climate Pack, Reconstruction Pack, Public Facilities Pack, and Emergency Response Pack.

Each pack must define required inputs, optional inputs, accepted semantic classes, accepted semantic attributes, validation gates, indicators, service features, workflows, exports, UI/report bindings, and authority review rules.

## Where Each Concern Lives

### PostGIS

PostGIS is the source of truth for city objects and semantic state.

PostGIS should own base physical entities, geometry, stable IDs, subtype tables, semantic class mapping, semantic attributes/tags, provenance and source evidence, authority/confidence/lifecycle status, semantic-pack outputs, indicators, and review decisions.

The current implementation already has:

- `ldt_core.entity_type_registry`;
- `ldt_core.city_entities`;
- subtype tables such as `ldt_core.building_entities`, `ldt_core.road_entities`, `ldt_core.facility_entities`, and `ldt_core.place_entities`;
- `ldt_query.city_objects`;
- `ldt_semantic.pack_registry`, `pack_rules`, `city_pack_bindings`, `service_indicators`, `service_features`, `service_workflows`, `pack_exports`, and `review_decisions`.

Needed additions:

- explicit infrastructure entity types such as water pipe, sewer pipe, stormwater pipe, street light, electric pole, transformer, pump station, drainage inlet, manhole, telecom/fiber segment, and utility service area;
- a semantic class registry instead of only hard-coded viewer/query classes;
- an entity semantic tag table for many-to-many object meaning;
- stronger links between source features, semantic tags, and authority review;
- semantic-pack output features that can be queried like normal city objects.

### Backend

The backend should not invent semantic meaning ad hoc in viewer code. It should read the PostGIS semantic model, enforce contracts, and expose stable APIs.

Backend responsibilities:

- build semantic query contracts from registry data;
- compile TwinQL/CQL2 against `ldt_query.city_objects`;
- validate semantic-pack manifests;
- run pack generators and validators;
- register pack outputs and artifacts;
- expose semantic-pack reports and exports;
- publish OGC/DCAT/NGSI-LD/FIWARE mappings where implemented;
- keep compatibility routes for older viewers while the PostGIS model evolves.

Current backend state:

- semantic class definitions are mostly hard-coded in `server/services/baseTwin/viewerContracts/semanticQueryContract.mjs`;
- `ldt_query.city_objects` is the canonical PostGIS query view;
- `server/services/ldtSemanticPackService.mjs` implements one reference pack, `reconstruction-service-core`;
- semantic-pack smokes prove the tables and reference pack can work, but this is not yet a general installable pack system.

Needed backend work:

- move semantic class definitions from hard-coded JS toward PostGIS/config-backed registry records;
- define a semantic-pack manifest loader;
- stop using one hard-coded pack as the module pattern;
- support utility/infrastructure entity families in query contracts;
- expose entity semantic context APIs for inspection panels and agents.

Implemented cut, 2026-06-26: `GET /api/live/:cityId/entities/:entityId/semantic-context`
and its `/current` alias return entity identity, semantic tags, source evidence,
mapping provenance, authority/review states, related rule checks, and summary
counts from PostGIS.

Implemented consumer cut, 2026-06-26: Analysis Selection members expose
`links.semanticContext`, and `GET /api/live/:cityId/analysis-selections/:selectionId/members?includeSemanticContext=1`
returns compact context for a capped member sample. This keeps selection/query
consumers on the same PostGIS-backed semantic contract.

### UI And Viewers

The UI should display and query semantic meaning, not define it.

UI/viewer responsibilities:

- show available semantic classes from the backend contract;
- let users query physical entities by semantic class, scope, and attributes;
- inspect a selected entity semantic context;
- distinguish base data, provider evidence, inferred attributes, and authority-approved states;
- show semantic-pack outputs only as outputs of explicit modules.

The UI must not decide that a road is a primary route, that a pipe is critical, or that an area is a flood risk. Those claims must come from PostGIS records, semantic rules, source evidence, or authority review.

## Examples

### Road Segment

```text
entity_type = road
semantic_class = mobilityNetwork
road_class = primary
traffic_role = arterial
surface = paved
emergency_access = candidate
source = OSM or Overture
authority_status = open-data
confidence = source-evidence
```

Relevant packs: Mobility Pack, Emergency Response Pack, Accessibility Pack, and Service Continuity Pack.

### Water Pipe

```text
entity_type = water_pipe
semantic_class = utilityNetwork
utility_type = potable_water
network_role = main_pipe
diameter_mm = 300
pressure_zone = zone_2
criticality = high
authority_status = authority-approved
```

Relevant packs: Water Infrastructure Pack, Leak Risk Pack, Emergency Response Pack, and Capital Maintenance Pack.

### Park Polygon

```text
entity_type = green_blue_system
semantic_class = greenBlue
category = park
vegetation = urban_green
public_access = true
heat_mitigation_role = candidate
stormwater_role = candidate
```

Relevant packs: Heat Pack, Flood / Drainage Pack, Public Space Pack, and Climate Adaptation Pack.

## Migration Direction

The platform should evolve in this order:

1. Keep `ldt_query.city_objects` as the stable query facade.
2. Extend `ldt_core.entity_type_registry` for utility and municipal infrastructure objects.
3. Add a semantic class registry and map current classes to it.
4. Add object-level semantic tags/attributes with provenance and authority state.
5. Refactor the hard-coded semantic query contract to read the registry.
6. Convert the reference semantic pack into an installable manifest-based pack.
7. Expose entity semantic context APIs for inspectors and agents.
8. Add first general municipal packs: Mobility, Urban Fabric, Utility Network, Green-Blue/Climate, and Civic Services.
9. Only then expose richer semantic-pack UX.

## Product Rule

No viewer, demo, or UI panel should make a semantic claim that is not backed by one of:

- a physical entity record;
- a semantic attribute/tag record;
- a source/provenance record;
- a semantic-pack rule/output;
- an authority review decision.

This keeps Twin Base Studio aligned with the Local Digital Twin direction: the city twin is not just a map, but a governed semantic model of the city.

It also keeps the product honest: a semantic pack or viewer is not operational
until it is attached to a named municipal workflow, reviewed by the relevant
authority role, and measured against a real workload-reduction target.
